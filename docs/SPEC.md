# Спецификация kv-lab 1.0

Этот документ описывает итоговую версию после этапа 6. Промежуточные версии намеренно имеют ограничения, которые разбираются в [практикуме](PRACTICUM.md). Журнал этапов 2–3 текстовый и несовместим с описанным ниже бинарным форматом.

## 1. Модель данных и границы

Ключ и значение — UTF-8 строки. Ключ: от 1 до 1024 байт. Значение: от 0 до 1 048 576 байт. Размер определяется в байтах, а не символах. Пробелы, переносы строк и Unicode допустимы. Значение может быть пустым. Ключи сравниваются побайтово, без Unicode-нормализации: визуально похожие строки могут быть разными ключами.

Текущее состояние — `map[string]string` в памяти. Журнал и снимок обеспечивают сохранение на диск. Данные должны помещаться в память. При создании снимка дополнительно нужна память для сериализованного JSON и кадра. Максимальный размер JSON снимка — 256 MiB. Это предел формата, использовать весь этот объём не обязательно.

Один каталог принадлежит одному открытому `Store`. Процесс может иметь несколько хранилищ в разных каталогах. Методы одного экземпляра выполняются по очереди под `mutex`. Нельзя копировать структуру `Store` или одновременно изменять переданный в `Batch` срез из другой горутины.

## 2. Интерфейс библиотеки

| Метод | Поведение |
|---|---|
| `Open(dir) (*Store, error)` | создаёт каталог при необходимости, берёт блокировку и восстанавливает данные из снимка и WAL |
| `Set(key, value) error` | создаёт или заменяет значение, подтверждает успех после `Sync` журнала |
| `Get(key) (string, error)` | возвращает значение или `ErrNotFound` |
| `Delete(key) error` | удаляет запись, отсутствие ключа не считается ошибкой |
| `Batch([]Op) error` | выполняет 1–1000 операций как одну атомарную запись журнала |
| `List(prefix) ([]Pair, error)` | возвращает копию пар, отсортированных по ключу. Пустой префикс выбирает все записи |
| `Snapshot() error` | сохраняет состояние и сокращает WAL до нуля |
| `Stats() (Stats, error)` | число ключей, последовательности, размер WAL и число байт восстановленного хвоста |
| `Close() error` | закрывает файлы и освобождает блокировку. Повторный вызов тоже успешен |

`Op.Type` принимает `set` или `delete`. У `delete` не должно быть непустого `value`. Порядок операций в пакете значим: `set x 1`, `delete x`, `set x 2` оставляет `x=2`. Валидация всего пакета предшествует любой записи. Одна ошибка отменяет весь пакет до обращения к диску. Максимальный **сериализованный** JSON одной записи — 16 MiB. Экранирование строк может увеличивать размер по сравнению с исходными значениями.

`sequence` увеличивается на 1 за успешную запись журнала: один `Set`, один `Delete` (включая отсутствующий ключ) или целый `Batch`. Чтения и снимки номер не увеличивают. `snapshot_sequence` — номер состояния опубликованного снимка. При достижении максимального `uint64` новые записи отклоняются.

## 3. Контракт сохранности

1. После успешного ответа операции её результат будет восстановлен после аварийного завершения процесса на локальной файловой системе в рамках проверенной модели.
2. До ответа результат может отсутствовать **или присутствовать целиком**: запись успела сохраниться, а ответ — нет. Отсутствие подтверждения не доказывает отсутствие записи. Это не exactly-once протокол.
3. Один пакет после восстановления применяется целиком либо не применяется. Половина операций пакета не видна.
4. Удалённые значения не воскресают после перезапуска или снимка.
5. Полный кадр с неверной контрольной суммой вызывает `ErrCorrupt`. Программа не пропускает его для чтения следующего кадра.
6. Только физически неполный последний кадр WAL считается оборванной записью и отбрасывается. Восстановление укорачивает файл до последнего проверенного кадра и вызывает `Sync`.
7. После ошибки записи/синхронизации WAL исход неизвестен: экземпляр переходит в состояние `ErrUncertain`. Нужно закрыть его и открыть заново. Все операции до переоткрытия, кроме `Close`, отклоняются.

Все успешные изменения вызывают `os.File.Sync`. Это важно для порядка сохранения, но выполненные тесты проверяют **SIGKILL процесса**, а не отключение питания. На macOS `fsync` не равен безусловному обещанию сохранения на физическом носителе при любой аппаратной неисправности. Отдельный `F_FULLFSYNC` здесь не применяется. Также не моделируются заполнение/отказ настоящего диска, повреждение файловой системы и потеря всей машины. Ошибки ввода-вывода в тестах имитируются управляемыми обёртками.

## 4. Файлы каталога

| Файл | Назначение |
|---|---|
| `LOCK` | файл для `flock`. **Не удалять при работающем процессе** |
| `wal.log` | последовательность кадров изменений |
| `snapshot.kv` | один полностью опубликованный кадр состояния |
| `snapshot.tmp` | незавершённый снимок. Игнорируется при запуске, перезаписывается следующим снимком |

Новые каталоги создаются с `0700`, файлы — с `0600` (с учётом umask). Права существующих каталогов не меняются. Защита от злонамеренного владельца каталога, подмены файлов/симлинков и обхода advisory lock посторонними программами не предоставляется. Не редактируйте эти файлы вручную и не используйте каталог внутри облачной синхронизации/NFS.

`LOCK` не означает «процесс работает»: блокировку хранит ядро, а файл остаётся. После `Close` или завершения процесса ядро освобождает блокировку. Удаление и создание нового `LOCK` при работающем процессе нарушает исключительность.

## 5. Формат кадра, little-endian

| Смещение | Размер | Содержание |
|---|---|---|
| 0 | 4 | ASCII `KVW1` для WAL или `KVS1` для снимка |
| 4 | 4 | длина JSON payload, uint32 LE |
| 8 | 4 | CRC32 IEEE от первых 8 байт заголовка |
| 12 | 4 | CRC32 IEEE от payload |
| 16 | N | UTF-8 JSON |

CRC заголовка защищает длину: повреждённая длина в полном заголовке должна стать ошибкой, а не причиной молча отбросить данные как «неполный хвост». Длина проверяется **до выделения памяти**. CRC32 выявляет случайное повреждение, но не умышленную подделку.

WAL payload:

```json
{"version":1,"seq":7,"ops":[{"type":"set","key":"name","value":"Анна"},{"type":"delete","key":"old"}]}
```

Снимок:

```json
{"version":1,"seq":7,"data":{"name":"Анна"}}
```

Неизвестные поля, неизвестная версия, некорректная операция, нулевой номер WAL, разрывы или повторы последовательности вызывают ошибку. Поле `data` снимка должно быть объектом. Пустой объект `{}` допустим, `null` — нет. После единственного кадра снимка не должно быть лишних байт. Неполный снимок — повреждение, не допустимый хвост.

JSON декодируется стандартным `encoding/json`. Повторяющиеся имена JSON-полей и Unicode escape-последовательности трактуются по его правилам. Формат не предназначен для обработки враждебных данных. Для CLI нужно передавать корректный UTF-8.

## 6. Запись

Под mutex: проверить состояние → проверить все операции → сериализовать весь пакет с `seq+1` → записать полный кадр → проверить число записанных байт → `wal.Sync()` → применить операции к map → увеличить seq → вернуть успех.

При частичной записи или ошибке `Sync` нельзя продолжать дописывать новые кадры тем же экземпляром: хвост журнала может быть неоднозначным. Используется `ErrUncertain` и переоткрытие.

## 7. Восстановление

1. Создать каталог при необходимости и захватить неблокирующий эксклюзивный `flock`.
2. Прочитать и полностью проверить `snapshot.kv`, если он существует. Временный снимок не участвует.
3. Открыть WAL. Если снимок с ненулевой последовательностью существует, отсутствующий WAL считается ошибкой открытия: его удаление не было шагом нашего алгоритма.
4. Читать кадры последовательно. Проверять заголовок, длину, CRC, JSON и семантику операций.
5. Кадры с `seq <= snapshot_sequence` уже учтены снимком: не применять их повторно, но проверять целостность и последовательность.
6. Каждый новый номер должен продолжать восстановленную последовательность ровно на 1.
7. Полный повреждённый кадр прекращает открытие с ошибкой. Неполный хвост обрезается до последней корректной границы.
8. Если снимок покрывает весь WAL, удалить содержимое старого WAL. Иначе сохранить его и установить позицию в конец.

Открытие не является чисто читающей операцией. Даже `get`, `stats` и `check` могут восстановить оборванный хвост или очистить полностью покрытый снимком старый журнал. `recovered_tail_bytes` показывает восстановление в **текущем открытии**, при следующем открытии обычно будет 0.

Внешнее удаление целых корректных кадров в конце WAL или всего каталога неотличимо от другой истории без дополнительного доверенного состояния. Нельзя обещать обнаружение любой ручной порчи/усечения. Не удаляйте журнал и не «чините» его редактором.

## 8. Снимок и порядок операций

Под тем же mutex:

1. Сериализовать `{version, seq, data}` и построить кадр.
2. Записать его в `snapshot.tmp` в том же каталоге.
3. Выполнить `Sync` временного файла и закрыть его.
4. `Rename(snapshot.tmp, snapshot.kv)` атомарно заменить снимок.
5. Синхронизировать каталог, закрепляя изменение его записи.
6. Обновить `snapshot_sequence` в памяти.
7. Укоротить существующий WAL до 0.
8. Вернуть файловую позицию в начало через `Seek`.
9. Синхронизировать WAL.

До публикации снимка источником восстановления остаётся предыдущий снимок + WAL. После публикации новый снимок уже содержит все изменения. Старый WAL может оставаться рядом: при восстановлении программа проверит его и пропустит уже учтённые номера. Поэтому ни один шаг не удаляет единственную актуальную копию состояния. Безопасность не требует атомарной замены двух файлов одновременно.

Снимок выполняется вручную и блокирует операции на время своей записи. Это осознанная простая реализация. Автоматическое создание, фоновая компакция, репликация и SQL не входят в интерфейс этого инструмента.

## 9. CLI

Формат: `kv -dir DIRECTORY COMMAND ARGS`. Флаги перед командой. Каталог по умолчанию `./data`. Shell самостоятельно разбирает кавычки, поэтому значения с пробелами заключайте в одинарные кавычки. Пустое значение задаётся `''`.

Успешные ответы — JSON, кроме `help` и `version`. `get` возвращает объект `key/value`, `list` — массив (включая `[]`), изменения — `{"ok":true}`, `stats`/`check` — поля статистики. Ошибки обычных команд идут в stderr.

| Код | Значение |
|---|---|
| 0 | успех |
| 1 | ошибка файловой системы/ввода-вывода, не отнесённая к другим категориям |
| 2 | аргументы/входные данные неверны |
| 3 | ключ не найден |
| 4 | каталог уже открыт |
| 5 | повреждённый формат/контрольная сумма |
| 6 | неопределённый исход изменения: нужен reopen |

`batch FILE` читает JSON-массив операций из файла. `batch -` читает его из стандартного ввода. `shell` держит хранилище открытым и читает по одному JSON-объекту на строку: `command`, `key`, `value`, `prefix`, `ops` по назначению команды. Пустые строки игнорируются. Переносы внутри значения нужно экранировать как `\n`. EOF (`Ctrl+D` на пустой строке) завершает сессию.

В JSONL-сессии ошибка отдельной команды возвращается в stdout как `{"ok":false,"error":"...","code":N}`. Обработка следующих строк продолжается. При выходе программа возвращает код последней ошибки или 0, если ошибок не было. Описание последней ошибки также идёт в stderr. После `ErrUncertain` следующие команды не восстановят хранилище — завершите сессию и откройте его снова.
